An AI coding agent can write a syntactically correct `DOWN` migration in seconds — one that drops the new column, restores the old constraint, and passes CI. What it usually can't do is tell you that the rollback will silently discard every row of data written into that new column since the migration went live. The script looks reversible. The deployment isn't. This is the gap between "rollback exists" and "rollback is safe," and AI-assisted migration tooling is making it easier than ever to ship the former while believing you have the latter.

## What's happening

Database migration tools have always generated `up`/`down` migration pairs, and reversing a schema-only change — dropping a table you just created, restoring a column you just dropped — is genuinely mechanical. AI coding agents are very good at that part. Several dedicated database-migration agents now map real dependency graphs and generate rollback scripts alongside the forward migration as a matter of course ([Augment Code, 2026](https://www.augmentcode.com/tools/8-ai-coding-agents-that-actually-accelerate-database-schema-migrations){:target="_blank" rel="noopener noreferrer"}), and the speed gain is real: what used to take a DBA an afternoon of writing and testing both directions of a migration now takes an agent minutes.

The problem is what happens in between the up and the down. A rollback is only truly safe when it can undo everything that happened while the new schema was live — not just the DDL, but the data written, transformed, or backfilled during that window. AI agents overwhelmingly generate the DDL-reversal half correctly and treat the data-reversal half as an afterthought, if they address it at all. Industry write-ups on 2026 rollback failures converge on the same root cause: the most dangerous failures are silent ones, where an agent is confidently wrong and throws no error at all ([Fast.io, 2026](https://fast.io/resources/ai-agent-rollback-strategy/){:target="_blank" rel="noopener noreferrer"}). A rollback script that runs clean and returns exit code 0 while quietly dropping three days of orders is worse than one that fails loudly, because nobody goes looking for damage that didn't announce itself.

Two recent, concrete incidents illustrate the range. In March 2026, a team rolled a payment service back from version 2.15 to 2.14 to fix a `NullPointerException`. The application code reverted cleanly, but the database schema stayed at 2.15 — the older code couldn't handle the new `payment_method_id` column, and 200 pods went into `CrashLoopBackOff` for a 98-minute outage, entirely because the rollback plan only covered code, not the schema-and-data state it depended on. In April 2026, an AI coding agent given an overly broad API token guessed a volume ID incorrectly and deleted a production database and all of its volume-level backups in nine seconds; the rollback failed completely because there were no deletion safeguards to roll back from in the first place ([Digital Applied, 2026](https://www.digitalapplied.com/blog/agent-rollback-checkpoint-patterns-2026-engineering-reference){:target="_blank" rel="noopener noreferrer"}). Neither incident was a "the AI wrote bad SQL" failure. Both were "the rollback plan didn't match what actually needed to be reversed" failures — and AI agents are, if anything, better than humans at producing plausible-looking rollback code that hides exactly this mismatch.

The industry's own best-practice pattern for zero-downtime schema changes — expand-contract — actually underscores the risk rather than solving it. Expand-contract works by adding new structure, dual-writing to old and new, migrating data over, then removing the old structure only once the new one is proven ([Prisma Data Guide](https://www.prisma.io/dataguide/types/relational/expand-and-contract-pattern){:target="_blank" rel="noopener noreferrer"}). Done correctly, this makes rollback genuinely safe at every phase, because the old structure and its data are still intact until the final contract step. But it only works if the agent's rollback script actually understands which of the three phases the migration is currently in, and AI agents asked to "add a rollback" typically default to a single generic down-migration rather than a phase-aware one — which is safe for the expand phase and actively destructive if invoked after the contract phase has already dropped the old structure.

## Who this affects

Database administrators and data engineering leads are the most immediately exposed, because they're the ones who get paged when a rollback that was supposed to be the safety net turns into the incident. Platform and DevOps teams who wire AI-generated migrations into automated CI/CD pipelines carry a second layer of exposure: once a rollback step is automated and trusted, nobody manually reviews it under pressure during an actual incident — that review has to have happened well before 2 a.m., or it doesn't happen at all. Engineering managers who've adopted AI coding agents for migration work specifically because of the speed gain need to understand that the speed applies unevenly: forward migrations and schema-only rollbacks get fast and reliable, while data-safe rollbacks stay just as hard as they always were, and an agent's confident output can mask that difference. This connects directly to the review-gap problem covered in [The Hidden Risk of Parallel AI Agents Merging DB Schemas](/blog/2026/08/15/parallel-ai-agents-schema-migration-review-gap/) — a rollback plan is one more artifact that needs a reviewer who understands the full picture, not just the diff in front of them.

Compliance and audit teams have a stake too, particularly in regulated data environments. A rollback that silently drops data isn't just an availability problem; if that data included records subject to retention requirements, the "successful" rollback is itself a compliance incident nobody logged as one.

## When this becomes a real problem

This isn't a future risk — it's already happening in production, as both 2026 incidents above show. What's changing is the rate at which it happens, because AI-assisted migration authorship is scaling faster than migration review discipline is. Teams that adopted AI coding agents for schema work in the past 12–18 months are now accumulating months of AI-authored rollback scripts that have never actually been exercised, because the forward migrations mostly succeeded and the rollback path was never triggered. That's the worst possible state: untested rollback code, growing in volume, with rising organizational confidence in it precisely because it hasn't failed yet. The realistic window for this to surface as a visible incident at any given organization is the next major forward migration that does need to be rolled back — which, for an actively developed schema, is a matter of months, not years.

## How this actually plays out in a database environment

The failure mode has a consistent shape. An agent proposes a forward migration: add a column, backfill it from existing data, then (in a later, separate change) drop the column it replaced. The agent also generates a rollback script for the initial migration, and that script is technically correct for the moment it was written — it drops the new column and nothing else exists yet to worry about. The migration ships. Over the following days or weeks, the application writes new data exclusively into the new column, because that's the whole point of the migration. Nobody regenerates the rollback script to reflect that new data now lives somewhere the original rollback doesn't know about.

Then an unrelated production issue triggers a rollback of that release. The automated pipeline runs the stored rollback script — the same one from weeks ago — which drops the new column exactly as designed. Every row of data written since the forward migration went live is gone, because it existed nowhere else. No error is thrown; `DROP COLUMN` succeeds every time you ask it to, regardless of how much data is in the column. The incident review afterward reveals the rollback script was never wrong, technically — it just described a system state that no longer existed by the time it ran.

This is exactly the class of problem the saga pattern exists to address for actions that span more than one system or more than one transactional boundary — but sagas require an explicit compensating action for every forward step, and there is no automatic derivation of a saga from a single AI-generated migration file. An agent has to be told, explicitly, to reason about data lineage and time-of-rollback state, not just schema state, or it will keep producing schema-only rollbacks that look complete.

## Actions to take now

1. **Audit your existing rollback scripts today**, starting with any generated by an AI coding agent in the last six months. For each one, ask a single question: does this rollback account for data written after the forward migration ran, or does it only reverse the DDL? Flag every script that fails this test — that's your actual exposure, not a hypothetical one.
2. **Require phase-awareness in any AI-generated rollback**, explicitly, in the prompt or the migration template: does the rollback know whether the migration is still in an expand phase (safe to reverse) or has already reached contract (old structure gone, rollback now destructive)? Don't accept a generic down-migration as sufficient for anything beyond the expand phase.
3. **Test rollbacks against a realistic copy of production data, not an empty schema.** A rollback script that "works" against a freshly migrated, still-empty table will pass every CI check and still destroy data in production, because the failure only shows up once real data has accumulated in the new structure.
4. **Set a hard rule: no rollback script goes into an automated pipeline without a human who understands data lineage reviewing it separately from the forward migration review.** Treat rollback review as its own gate, not a rubber-stamp attached to the forward PR — the forward migration and the rollback plan have different failure surfaces and need different scrutiny.
5. **Re-generate or re-verify rollback scripts on a schedule, not just at migration time.** A rollback written the day a migration shipped can be stale within a week if the new structure starts accepting writes. Tie rollback-script freshness checks to your regular migration audit cadence, not a one-time review.
6. **Restrict the credentials available to any agent capable of running a rollback or destructive DDL in production**, independent of the rollback-quality problem — the April 2026 volume-deletion incident happened specifically because an agent held broader API privileges than its task required. Least-privilege scoping doesn't fix bad rollback logic, but it bounds the blast radius when a rollback does the wrong thing.
7. **Build the saga/compensating-action pattern into any migration that spans more than one system** (database plus external API, database plus cache, database plus search index) rather than relying on a single migration file's rollback to cover all of it. No AI agent will infer a multi-system compensating transaction from a single-table migration prompt — that has to be designed in explicitly.

## Key takeaways

- AI coding agents reliably generate correct schema-reversal (DDL) rollbacks but routinely omit safe handling of data written after the forward migration ran.
- The most dangerous rollback failures are silent: the script executes successfully while discarding data, with no error to alert anyone.
- Real 2026 incidents — a payment-service schema/code mismatch causing a 98-minute outage, and an AI agent's mistaken database deletion with no working rollback — show this is a current, not future, risk.
- The expand-contract pattern only stays safe if the rollback script is phase-aware; a generic down-migration becomes destructive once the contract phase has run.
- Rollback scripts need their own review gate, their own testing against realistic data volumes, and periodic re-verification — not a one-time check at migration time.
